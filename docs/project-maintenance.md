# 專案資料與發佈管理

## 版本控制

Git 保留 `lieta_automator/`、`tests/`、`docs/`、入口程式、依賴清單、打包設定及介面所需的 `settings.png`。`tests/` 內包含可重複執行的單元測試、Chrome 整合測試與明確啟動的實站對照工具；測試程式與測試產物應分開管理。

執行檔與發佈 ZIP 放在 GitHub Releases。登入 Profile、使用者設定、ticker 清單、批次紀錄、AI 控制資料、下載內容、截圖、日誌與打包產物不得加入 Git；新增忽略規則不會自動移除已追蹤檔案。

## 本機資料保留

- `automation_profile*/`、`user_settings.json`、ticker 清單與捷徑：保留原位，避免破壞登入與操作設定。
- `runs/`、`agent_runs/`、`agent_control/`：保留原位，供續跑、任務查詢與命令去重使用。
- `tests/`：保留測試原始碼；`.test-output/` 中的一次性輸出可封存。
- `build/`、Python 快取：確認沒有打包或測試程序使用後可刪除；`.build-deps/` 保留供下次打包使用。
- 舊版執行檔：保留安裝資料夾中的原檔。只有與安裝原檔 SHA-256 完全相同的 `dist/` 重複副本才可清除。
- `log_*.jsonl`、`temp_downloads/`：先確認沒有使用中的批次。已關閉的舊日誌與逾一天的下載暫存可壓縮封存，驗證 ZIP 內每個檔案的 SHA-256 後才移除原件；保留近期與使用中的檔案。暫存 HTML 不等於失敗項目，正式結果可能已複製至目的地。

本機封存位於 `.cleanup-archive/<日期>/`，不進入 Git 或 Release。每次整理保存逐檔清單、原始相對路徑、校驗值及處理結果。需要舊診斷資料時，先解壓至獨立資料夾查閱，不直接覆蓋目前資料。

## 發佈檢查

1. 核對執行檔版本與對應標籤；文件整理不改寫既有標籤。
2. 使用明確檔案清單建立下載包，只收錄執行檔、使用說明、任務範例及校驗檔；不壓縮整個工作目錄或安裝資料夾。
3. 核對壓縮包內容與 SHA-256，再上傳 GitHub Release，確認附件名稱、大小及校驗值。
4. 保留舊版 Release。清理目前主分支不會清除 Git 歷史；歷史改寫與遠端強制更新需另行協調。
